**Date:** 2026-08-08
**Auditor:** HUB-Claude (interactive, with dp)
**Baseline:** web4 `origin/main` @ `c929419`; hestia `origin/main` @ `5b10904`
**Method:** every finding below was checked against the **binary or the source**, not against

`hestia/docs/STATUS_AUDIT_2026-08-08.md` (baseline `9a6a5c2`), which uses the right distinctions —

## Severity 1 — a doc that teaches a silent no-op

### D1. `hub/docs/HUB-LAW.md` names an action that does not exist

`HUB-LAW.md:185` tells an operator to write:

```yaml
r6.request.action == "assign_role"
```

The action the gate actually evaluates is the **HubEvent kind**, which is **`role_assigned`**
(`hub-lib/src/events.rs:617`, `build_r6_request` sets `action: event.kind()`). The shipped starter
law is correct — `hub up` writes `value: role_assigned` — so **the template disagrees with the doc
that explains the template.**

Why this is severity 1 rather than a typo: **an unmatched norm is not an error, it is an allow.**
A norm naming a non-existent action never fires, produces no warning, and is indistinguishable at
runtime from a norm nobody wrote. An operator who follows this doc to restrict role assignment gets
a law that reads as restrictive and behaves as `DEFAULT-ALLOW`.

Compounding: **nothing validates that a norm's action value is a real event kind.** No parse-time
check, no lint, no test. Verified — zero references to `kind()` in `hub-lib/src/law.rs`.

Also affected (same wrong value, in test fixtures rather than shipped law):
`hub-lib/src/law.rs:529`, `hub-lib/src/law.rs:837`, `hub-daemon/src/rest.rs:7370`. Those parse
fine, which is precisely the problem — the tests cannot catch this class because nothing checks it.

**Remedies, in order of value:**
1. A guard that fails when a norm's `r6.request.action` value is not a known `HubEvent::kind()`.
   This is the fix that makes the whole class impossible; the doc fix alone leaves the next
   author free to repeat it.
2. Correct `HUB-LAW.md:185` to `role_assigned`.
3. Publish the enumerated action list in `HUB-LAW.md` — see D4.

## Severity 2 — shipped surfaces with no documentation

### D2. The discussion surface (Track H) is entirely undocumented

Merged 2026-08-07 (`85975dc`, PR #650) and shipping: `POST` actions `create_topic` / `add_post`,
`GET /v1/hubs/:id/topics`, `GET /v1/hubs/:id/topics/:tid`, `GET /discuss`, and the `topic_created` /
`post_added` event kinds.

Searched `hub/**/*.md`, `web4-standard/**/*.md` and `docs/**/*.md` for every one of those
identifiers: **zero hits.** Not in `hub/README.md`, `QUICKSTART.md`, `HUB-LAW.md`, `PRD.md`,
`SPRINTS.md`, or `V2-V3-ARCHITECTURE.md`.

This is my own omission — I built it and did not document it.

Specifically owed:
- **README / PRD**: the surface exists and what it is for.
- **HUB-LAW.md**: `topic_created` and `post_added` are law-governable action kinds, and the starter
  law names **neither**, so both currently ride `DEFAULT-ALLOW` by omission. The starter law's own
  comment says "extend this list as new consequential kinds land" — it has not been extended.
- **Locked-tier behaviour**: `/discuss` and `/topics` are **not** in the tier-0 allowlist, so a
  locked hub answers **503**, not an empty forum. Correct (fail-closed beats a 200 that reads as
  "nothing was ever said") and surprising enough to be worth one line.

### D3. `QUICKSTART.md` never mentions `hub up`

`hub up` is the turnkey path — five deployment archetypes, a fail-closed starter law, an operator
token, and a printed go-live runbook. Its own output describes it as "one command for operators with
no IT background."

`grep -c 'hub up' hub/docs/QUICKSTART.md` → **0**.

So the document whose job is "time to first running chapter: 10–30 minutes" walks a newcomer
through eight manual steps while the one-command path goes unmentioned. It **is** in `README.md`
and `STATUS.md`; the getting-started doc is the one place it is absent.

Related, measured: **15 of 28 CLI commands are absent from QUICKSTART** — `up`, `set-law`,
`get-law`, `init-law`, `assign-role`, `council`, `set-profile`, `set-member-key`, `remove-member`,
`seal-identity`, `rotate-passphrase`'s siblings, and the `pair-*` family. Several are legitimately
advanced, but **the entire law workflow (`init-law` → `set-law` → `get-law`) is missing from the
getting-started path**, and law is the hub's central concept.

## Severity 3 — stale or incomplete against verified behaviour

### D4. No document enumerates the valid `r6.request.action` values

`HUB-LAW.md` explains the selector grammar and gives examples, but there is no list of what an
action may be. The values are `HubEvent::kind()` strings; an author must read Rust to find them.
This is the soil D1 grew in. One generated table would close D1, D2's law half, and this.

### D5. QUICKSTART Step 4's identity one-liner cannot work

```bash
ALICE_ID=$(python3 -c "import json; print(json.load(open('alice.json'))['lct']['id'])")
```

`gen-lct` writes an **encrypted vault**; the file is not JSON. Executed:
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0x89`. The doc contradicts its own Step 2,
which says the identity is encrypted.

**Workaround, verified:** `gen-lct` prints the id on stdout (`LCT id:  300cbfc9-…`). Capture it
there, or use the request-driven join path in the same step.

### D6. `set-law` silently overwrites `<hub-dir>/hub-law.yaml`

Undocumented, and it destroys the baseline: applying an amendment overwrites the starter law in the
hub directory, so "revert to the original" fails unless a copy was kept elsewhere. Hit during the
hackathon rehearsal; recovered by regenerating the template with `hub up` into a scratch dir.

Owed: one line in `HUB-LAW.md` — keep amendment files **outside** the hub directory.

### D7. `TROUBLESHOOTING.md` has no entry for the law-integrity 409

`grep -c '409|integrity'` → **0**. TROUBLESHOOTING is otherwise good and current (2026-08-07, covers
the locked-hub 503 well), but this is the most opaque failure the hub has: **every** governed write
starts returning 409 and the cause is invisible from the request.

Note this interacts with **PR #667** (open): `reload-law` reloaded the law but not the ledger, so
`hub set-law` against a running hub wedged writes until restart. With #667 the documented flow
works; without it the TROUBLESHOOTING entry is urgently needed. Either way the entry is owed,
because a genuine divergence still produces the same 409.

### D8. `reload-law`'s response is documented without its verdict field

`HUB-LAW.md:96` shows `POST /v1/admin/reload-law`. PR #667 adds `law_integrity` (`ok` / `mismatch` /
`unverifiable`) to the response, precisely because `reloaded: true` answered the wrong question.
Doc update owed **on merge**, not before.

### D9. QUICKSTART Option B recommended a Docker path that could not build

Until PR #655 (merged 2026-08-07) `hub/Dockerfile` omitted the `web4-policy` path dependency and
pinned `rust:1.83`, below the 1.91.1 floor `aws-config` declares. Two independent build failures.
QUICKSTART presented it as a co-equal option.

Now fixed in source. **Still owed: someone with Docker must actually run
`docker build -t hub:test -f hub/Dockerfile .`** — I could not (no Docker on HUB) and did not claim
the image builds green. Until someone does, Option B is unverified rather than known-good.

## Proposed order of work

Ordered by *harm prevented per unit effort*, not by severity label:

1. **D1 guard** — reject a norm whose action is not a real event kind. Kills the silent-no-op class
   rather than one instance. Small.
2. **D1 doc fix + D4 action table** — same edit; the table is what stops it recurring.
3. **D2 Track H docs** — mine to write, and the surface is live.
4. **D3 `hub up` in QUICKSTART** — highest reader impact of anything here.
5. **D7 TROUBLESHOOTING 409 entry.**
6. **D5 / D6** — two small QUICKSTART/HUB-LAW corrections.
7. **D8** on #667 merge; **D9** needs a machine with Docker, not a doc edit.
8. **D-currency** — STATUS/CHANGELOG refresh; lowest urgency, highest surface area.
